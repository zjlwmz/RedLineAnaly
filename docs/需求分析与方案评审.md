# 《红线叠加分析技术方案》需求分析与评审

> 针对 `红线叠加分析技术方案.md`（分布式版）的落地评审。结论先行：**需求成立、架构方向正确，但原方案有 6 处会导致错误结论或无法运行的问题**，均已在本仓库实现中修正。演示系统已在云端跑通端到端。

---

## 1. 需求本质

一句话：**拿一个输入区域面，与全国管控红线图斑做空间叠加（Intersect），回答三个问题——**

1. 压没压？（是否相交）
2. 压了什么？（红线类型：生态保护红线 / 永久基本农田 / 城镇开发边界）
3. 压了多少？（重叠面积、占输入面比例 → 合规结论）

分布式只是手段：按输入面实际涉及的省份动态拆分子任务，避免全国 30+ 省空跑。

### 隐含需求（原方案没写但必须有）

| 隐含需求 | 为什么必须有 |
|---|---|
| 坐标基准统一 | 输入可能是 WGS84 GCJ-02 等，红线是 CGCS2000，不统一则相交结果整体漂移 |
| 面积口径 | 占比是合规判定的依据，算错面积=结论错误 |
| 省界边界容差 | 红线数据按省裁剪存储时，骑省界的图斑两边都不完整 |
| 部分失败处理 | 3 个省的任务 1 个超时，结果算什么？不能挂死也不能静默给错结论 |
| 数据版本追溯 | 合规结论要能回答「你用的是哪一版红线」 |
| 输入防御 | 用户传一条线、一个自相交多边形、一个 13 万 km² 的巨型面，都不能把系统搞挂 |

## 2. 原方案的 6 处问题与修正

### 2.1 占比公式在跨省时会超过 100%（严重）

原方案：`Ratio = S_overlap / S_original`，其中 S_overlap 是各省结果相加。

问题一：**S_original 用什么**？若用「各省片段面积相加」，因为省界数据重叠/缝隙，可能 ≠ 输入面真实面积。
问题二：**红线之间互相重叠**。生态保护红线与永久基本农田在真实数据里经常叠在同一地块（多规合一前的历史遗留），逐类型相加会重复计数。

修正（双口径并行，都给用户，避免客户拿错数字）：
- `sum_overlap_area_m2`：各图斑相加口径（兼容原方案字段 `overlap_area` / `overlap_ratio`，展示时封顶 100%）
- `union_overlap_area_m2`：所有重叠区域先做几何 **Union** 再算面积 —— 这才是「真正被红线盖住的面积」
- 严重压盖判定用**并集口径**。

实测：晋冀太行用例，相加口径 114%、并集口径 100.01% —— 原方案会把这种数字直接报给客户。

### 2.2 `GetArea()` 算出来的是平方度（严重）

原方案代码在 EPSG:4490（度为单位）上直接 `overlap_geom.GetArea()`。1 平方度 ≠ 1 平方米，差 9~10 个数量级；若改用 Web 墨卡托（EPSG:3857）算面积，高纬度（黑龙江）面积虚高可达 60%+。

修正：
- 面积一律投影到 **以区域中心自定义的 Albers 等积圆锥** 后计算（误差 <0.01%）
- 同时用 pyproj `Geod`（Karney 椭球算法）算椭球面积做**交叉校验**，差异 >0.5% 告警
- 按米缓冲同样先投影（原方案在经纬度上 `Buffer(0.0005)` 这种写法纬度越高圈越小）

### 2.3 Shapefile 不适合做全国红线载体（工程）

.shp 有 2GB 单文件上限、字段名 10 字符、无内建空间索引。全国生态红线图斑量级在百万级，逐要素 `for feature in layer` 全表扫不可接受。

修正：**GeoPackage + R 树空间索引**；查询走 `SetSpatialFilterRect(bbox)` 粗筛，候选才进内存精算。实测单省 8 图斑数据无感，但架构上为百万级留好了路径。

### 2.4 「bbox 相交 = 该省有任务」不成立（正确性）

只做包围盒相交：bbox 跨省但面实际只在一个省 → 多拆空任务；面贴省界 → 漏拆。

修正：两级判定 —— bbox 快速排除 → 包围盒几何相交 → **实际几何 Intersects** 才算命中，同时记录每省内的面积占比（前端展示「该面 85% 在北京、15% 在河北」）。

### 2.5 消息体设计矛盾（架构）

原方案「消息体只携带图斑 ID，节点自行拉明细」——但计算节点还必须知道**输入面的几何**才能做相交，方案里没交代怎么传。几何走消息体（WKT）小面没问题，大面（几百公里）WKT 可能几 MB，会拖垮 MQ。

修正：消息体携带 `input_wkt` + `input_srid` + 预计算的 `input_area_m2`（各 worker 不用重复算）；主节点入口限制单面 ≤2000 km²，超大面走批处理/裁片路线（`app/tiling.py` 已备）。生产对接对象存储时把 WKT 换成 OSS key 即可，接口已留 `input_wkt` 字段位。

### 2.6 「必要时对红线做缓冲」一句话带过（正确性）

这句话其实是**必须项**：红线数据按省裁剪存储时，省界处的图斑被切开，若输入面恰好贴着省界，不缓冲必漏判。

修正：红线在相交前按 `buffer_m`（默认 50m，可配）外扩；缓冲只在候选图斑上做（粗筛之后），代价可控。同时警惕反向问题——缓冲会让结果略偏大，所以 buffer 是参数而非硬编码，且结果里记录 `buffer_m` 供追溯。

## 3. 架构修正：fanout 而不是单队列

原方案「N 个子任务投递到一个队列，各节点消费」在按省拆分时是**错的**：一条消息只能被一个消费者取走。河北任务被 worker-A 消费、北京任务被 worker-B 消费后，队列里就没了，但两个 worker 的结果都要回来 —— 消费 ≠ 处理完所有省。

实际采用的拓扑（`app/topology.py`）：

```
exchange: redline.overlay (direct, durable)
  ├── routing: task.worker-1 → queue redline.task.worker-1   （每节点独占，prefetch=1）
  ├── routing: task.worker-2 → queue redline.task.worker-2
  ├── routing: result        → queue redline.result          （主节点统一收）
  └── routing: dead          → queue redline.dead            （失败/超时消息，可重放）
```

- 主节点按省数把任务轮询发给在线节点（`app/registry.py` 负责发现：静态名单 → Redis 心跳 → 本地进程扫描，三级降级）
- AMQP 0-9-1 没有「列出队列绑定」的协议方法，worker 发现不能靠反查 exchange，这点原方案没考虑
- 任务消息持久化 + 60s 过期，防堆积；worker 失败时把错误回传 result 并 ack（不 requeue，避免毒消息死循环），同时进死信
- RabbitMQ 不可用时**降级本地串行计算**（demo 友好；生产环境应改为直接报错）

## 4. 合规判定分级

原方案只有 `is_compliant: false`，太粗。实现为四级：

| 级别 | 条件 | is_compliant |
|---|---|---|
| CLEAR | 并集压盖面积 ≈ 0 | true |
| OCCUPIED | 0 < 占比 < 阈值 | false |
| SEVERE | 占比 ≥ 阈值（默认 50%，**必须与客户确认**） | false |
| OUTSIDE | 输入面显著出界 | null（结论无效） |

幂等：`task_id = batch_id:province_code`，同一 task 重复投递以第一条成功结果为准；批次查询接口 `GET /api/v1/overlay/jobs/{batch_id}` 可看每个省的回传明细（哪个节点算的、耗时、数据版本）。

## 5. 演示数据说明（重要）

当前 `data/redline/` 下的红线是**按真实地理语义摆放的合成数据**（太行山生态带故意骑在晋冀省界、廊坊北三县耕地故意压京冀交界、白洋淀城镇边界等），用于验证链路正确性。**生产必须替换为自然资源部门下发的标准红线数据与标准省界**（当前省界来自公开网络数据，有自相交、精度 ~1km，已做 MakeValid 兜底，但不能用于正式合规判定）。

## 6. 端到端验证结果

6 个用例全部通过（`tests/e2e_test.py`，RabbitMQ 分发模式）：

| 用例 | 识别省份 | 结论 | 相加/并集占比 |
|---|---|---|---|
| 廊坊大城 压城镇边界 | 冀 | 严重压盖 | 80.23% |
| 北京朝阳 压基本农田 | 京 | 严重压盖 | 70.59% |
| 北京东部山区 跨省 | 京+冀 | 严重压盖 | 100.00 / 100.01% |
| 山东空白区 | 鲁 | 未压盖 | 0% |
| 天津北部 包围盒跨省 | 津+冀 | 严重压盖 | 71.60% |
| 京津冀北部 三省面 | 京+津+冀 | 严重压盖 | 100.00 / **91.03%**（相加口径虚高的实证） |

鲁棒性：自相交多边形自动修复 ✓、线几何 400 ✓、超大面积拦截 ✓、MQ 宕机降级本地 ✓。
